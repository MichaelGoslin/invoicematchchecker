# Technical notes

How each part of AP Verify works, for developers reading the code. For what the app does and how to run it, see the [README](../README.md).

## Status

App (Next.js 16): `/` is the review queue (sample sets when no database is set), and `/try` uploads one set (PO, optional receiving report, invoice) to `POST /api/match`, which reads the documents with Claude, runs the rules and returns the traces and decision. `proxy.ts` gates every page and API route behind `APP_PASSCODE`; a production deploy without it returns 503. With `POSTGRES_URL` set, every set, its recommendation and the engine snapshot are saved to Postgres, and the queue lets a named reviewer approve or reject each set. Going against the recommendation is an override and needs a written reason. Every recommendation and decision goes into an append-only `audit_log`, and every stored invoice that wasn't rejected feeds the duplicate check, including ones still pending, so a resubmission is caught before the first copy is decided. Without a database, nothing is saved and the duplicate check returns Needs review. The queue groups pending sets by why the engine placed them, shows each check side by side, and takes a reason code for overrides.

Batch (stories 1 and 5): `/batch` takes the morning batch of POs, receiving reports and invoices in any order. Each file is read on its own request (four at a time), then `POST /api/batches/:id/match` joins each invoice to the PO and receiving report that share its PO number and runs every set. Documents it can't place, such as unknown types, uncertain or shared PO numbers, or a PO no invoice cites, are set aside with a reason, never guessed. An invoice that clearly cites a PO that isn't on file is incomplete, not rejected; an uncertain PO reference gates the set. On the queue, "Approve all clean" approves only sets the engine recommended with no uncertain reads, and "Export approved" downloads a CSV for the ERP. Each set is exported once and logged, and cells are protected against spreadsheet formula injection (a cell starting with `=` or a similar character that a spreadsheet would run as a formula).

Extraction: `extractDocument` in `lib/extract` reads a PDF, image or text document with Claude (`claude-opus-5-5`, structured output) into fields that each carry a value, confidence, quoted evidence and page. Code then checks each value against its quoted text and lowers confidence when they disagree; it never raises it. `toMatchInput` maps a PO, an optional receiving report and an invoice into the engine's input, and `runSet` runs every rule and decides. Tests use a fake client and make no API calls.

Engine: all match rules return a decision trace and share the confidence fail-safe (tested): PO on file (none recommends reject), receiving report on file (none makes a 3-way match incomplete; 2-way only when chosen), vendor, PO number, duplicate, quantity vs ordered and received, unit price (2% and a $50 extended-cost cap, where extended cost is units × the price difference), line total and invoice total. `decideSet` turns a set's traces into Recommend approve / Needs review / Recommend reject, and `compareForQueue` sorts the review queue. Tests run in GitHub Actions on every PR, including a score against the 100-set answer key in `sample-data/output` (99 of 100 agree on printed values; the scan, S-087, depends on extraction). The UI contract is `TraceEntry` and `SetDecision` in `lib/match`; sample sets with answer keys are in `lib/match/fixtures.ts`. Explanations (step 5): on any set with findings, "Explain in plain English" asks Claude to restate the decision and its findings in two to four sentences. Claude sees only the decision and the findings, is told to treat document text as data, and can't change the outcome. If its text cites any number the findings don't contain, it is discarded and the rules' own summary is shown instead. Each set is explained once and the result is stored. The full requirements are in the team PRD.

Documents: each upload is stored with what was read from it, and the queue links to the invoice, PO and receiving report behind a set. `GET /api/documents/:id` checks the passcode itself before any lookup, looks up only ids shaped like the ones the app makes, serves exactly the stored type with `X-Content-Type-Options: nosniff` and `Cache-Control: private, no-store`, encodes the file name, and sandboxes text files. `proxy.ts` lets only `/login` itself through signed out. A path that merely starts with "login" is gated.

## Local environment files

`npm run dev` also loads `.env.development.local`, which takes priority over `.env.local`. Our team keeps the shared `POSTGRES_URL` there, so for us local uploads land in the shared queue. A fresh clone has no such file and only needs `.env.local`.
